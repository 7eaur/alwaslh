# Stage 10 — Media Pipeline Architecture

## Purpose

Provide one deterministic, server-side media pipeline for curriculum source assets and Admin uploads without inheriting the legacy browser-processing defects.

## Legacy evidence

Legacy `src/lib/file-processing.ts`:

- configures PDF.js worker from external `unpkg`;
- compresses images in the browser;
- renders PDFs in the browser;
- accepts unsupported files by passing them through;
- on processing failure may keep the original file silently;
- `processFiles()` appends worker results to one shared array, so concurrent completion order can reorder the user's files/pages;
- image compression and AI optimization are duplicated concerns tied to browser memory.

Stage 10 does not reuse this runtime design.

## Target flow

```text
input descriptor / upload
→ validate type + size + declared source order
→ source bytes persisted in staging
→ PDF page extraction when needed
→ stable logical page identities
→ bounded image transforms
→ display variant
→ thumbnail variant
→ AI variant
→ deterministic storage keys + SHA-256
→ metadata transaction
→ publish/attach
```

## Invariants

1. **Input/source order is authoritative.** Completion order is never used as page order.
2. Each logical page receives an immutable `position` before concurrent processing starts.
3. Unsupported MIME/extensions are rejected explicitly; there is no silent pass-through.
4. A failed transform cannot be reported as successful by falling back silently to the original.
5. Source bytes and derived variants have independent checksums and storage keys.
6. Storage keys are generated by trusted backend code only and cannot contain traversal components.
7. File-system paths are an implementation detail. Database/storage contracts use opaque relative keys.
8. Stage 9 source provenance (`content_source_asset_id`, source path/order/blob SHA) survives processing.
9. Metadata is committed only after required stored objects exist.
10. Partial failure is observable/retryable; it never changes ordering.
11. Compression prioritizes readable educational text over smallest byte size.
12. PDF extraction runs server-side with a locally installed/runtime-verified tool; no CDN worker.
13. Concurrency is bounded independently for source items and page transforms.
14. Temp files are scoped to one operation and cleaned on success/failure/abort.
15. Identical deterministic input can be retried without creating conflicting media identity.

## Runtime choices

### Image transforms

Use `sharp` in the Backend/worker runtime for metadata, resizing, JPEG/WEBP encoding and thumbnails. This keeps processing out of Admin browsers and gives one implementation for imported and uploaded media.

Initial profiles are intentionally conservative and must be tested on educational scans:

- **display:** preserve aspect ratio, max long edge 1800 px, high-quality WEBP/JPEG chosen by source/quality evidence;
- **thumbnail:** max long edge 480 px;
- **AI:** max long edge 1280 px, bounded bytes/quality while retaining legible text.

The exact quality parameters are Stage 10 runtime-test outputs, not immutable product rules.

### PDF extraction

Use Poppler `pdftoppm`/`pdfinfo` on the server. Runtime startup/CI must verify these binaries exist. PDF pages are rendered to deterministic page-numbered image files, then fed into the same image pipeline.

Reasons:

- no browser memory dependence;
- no external PDF worker CDN;
- mature headless PDF rasterization;
- straightforward page-count and failure inspection;
- easy to test in CI and same-host deployment.

If production hosting later cannot provide Poppler, that is an infrastructure blocker to resolve explicitly; do not silently switch to a remote worker.

### Storage

Stage 10 starts with a **filesystem-backed storage adapter** rooted at `MEDIA_STORAGE_ROOT` on the same hosting environment, because the product currently targets one self-hosted backend/database environment and no object-store requirement has been established.

The adapter contract keeps opaque relative keys so an S3-compatible adapter can be introduced later without changing domain/database identities.

Production requirements for the root:

- outside application source tree;
- writable only by the application service account;
- not directly directory-listed by the web server;
- durable volume included in host backup/restore policy;
- capacity/usage monitored later under Operations.

## Storage key contract

```text
media/{logicalAssetId}/source/{sha256}.{ext}
media/{logicalAssetId}/display/{profileVersion}-{sha256}.{ext}
media/{logicalAssetId}/thumb/{profileVersion}-{sha256}.{ext}
media/{logicalAssetId}/ai/{profileVersion}-{sha256}.{ext}
```

`logicalAssetId` is backend-generated. Keys are normalized POSIX-style relative paths and validated before any filesystem join.

## Data model direction

Stage 9 `content_source_assets` remains source inventory/provenance.

Stage 10 introduces processing/storage identity rather than mutating Stage 9 inventory into lesson content directly. Required relationships:

```text
media_assets
  id
  content_source_asset_id?  -- imported source provenance
  kind/source mime/order/status
  original checksum + dimensions/page metadata

media_variants
  media_asset_id
  variant_kind = source|display|thumbnail|ai
  profile_version
  storage_key
  mime_type
  byte_size
  width/height
  checksum_sha256
```

Lesson attachment is explicit via `lesson_assets`; no lesson is inferred from source filenames.

## Upload boundary

Admin HTTP upload endpoints are not required to close the low-level pipeline itself if Admin Product routing/UX is later Stage 13. Stage 10 must nevertheless expose a tested backend service/CLI contract that Stage 13 can call without reimplementing processing.

## Errors and retry

Classify at minimum:

- `invalid_input`
- `unsupported_media`
- `source_read_failed`
- `pdf_inspection_failed`
- `pdf_render_failed`
- `image_decode_failed`
- `transform_failed`
- `storage_write_failed`
- `metadata_commit_failed`
- `aborted`

Retry is safe only from stable source identity/order. Processing attempts never derive order from retry timing.

## Security boundaries

- reject path traversal/storage-key injection;
- validate actual decodable media, not filename alone;
- cap input bytes/page count/dimensions to prevent resource exhaustion;
- no shell command interpolation: use argument arrays with `spawn`/`execFile`;
- temp directories are random/scoped and never user-controlled paths;
- no client-supplied authoritative checksum/dimensions/order after processing;
- no SVG/script-capable file pass-through in the curriculum image pipeline.

## NOT YET VERIFIED

Until Stage 10 executable gates run, the following remain `NOT YET VERIFIED`:

- `sharp` runtime on CI/target hosting;
- Poppler runtime and page extraction;
- actual quality/legibility profiles;
- filesystem storage permissions/durability in production hosting;
- large-PDF memory/time behavior;
- abort/retry behavior under killed processing;
- real Admin HTTP upload integration (Stage 13 unless needed earlier for pipeline verification).
