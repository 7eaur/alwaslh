# Canonical PostgreSQL Schema Map

This document is the human-readable map for the rebuilt **الوسيلة الذكية** database. SQL migrations remain the executable source of truth.

## Identity

```text
profiles
  id UUID PK
  auth_subject UNIQUE nullable until auth binding
  role student|admin
  status
```

All student-owned records point to `profiles.id`. Access codes, device IDs and fingerprints are never ownership keys.

## Curriculum

```text
classes
  1 ── * subject_class_links * ── 1 subjects
                 |
                 └── lessons
                        |
                        └── lesson_assets (stable position)
```

A lesson cannot reference a subject that is not actually linked to its class because `(class_id, subject_id)` is a real composite FK.

`lesson_assets.position` is unique per lesson, so concurrent upload completion cannot reorder pages.

## Access / entitlement

```text
full_access_codes ─┐
                   ├── access_redemptions ── student_entitlements ── profiles
class_access_codes ┘                                  |
                                                    classes (class scope only)
```

- Full access code: exactly 6 digits.
- Class access code: exactly 7 digits.
- Active all-content entitlement: max one per student.
- Active class entitlement: max one per student/class.
- Redemption uses an idempotency key and will be implemented as one server transaction.

## Quizzes / practice

```text
quizzes
  ├── quiz_lessons ── lessons
  └── quiz_versions
        └── questions
              └── question_options

practice_sessions
  ├── practice_session_questions
  │     └── practice_session_options
  └── practice_answers

practice_sessions ── quiz_attempts
```

Important design decisions:

- question identity is UUID, never array index;
- question order is persisted per practice session;
- option order is persisted per question/session;
- an answer can reference only an option belonging to that same question;
- one question has at most one correct option in the current MCQ/TF model;
- attempt percentage is generated by PostgreSQL from counts;
- finalization logic in the backend must derive counts from persisted answers, never trust client score input.

## Saved questions / achievements

```text
profiles ── saved_questions ── questions
profiles ── student_achievements ── achievement_definitions
```

Saved question identity cannot collide across lessons because the real question UUID is used.

Achievements are definitions plus server-derived awards. The browser does not invent awards.

## Notifications

```text
notifications
  target = global OR one profile OR one class
notifications ── notification_reads ── profiles
```

A notification may not simultaneously target one profile and one class.

## AI

```text
ai_jobs
  └── ai_job_units
        └── ai_outputs
```

The browser creates/observes work; durable server workers own execution.

`ai_jobs` stores prompt key/version, idempotency, progress and lifecycle. `ai_job_units` stores deterministic work units, attempts and selected provider aliases. `ai_outputs` stores raw/normalized output plus validation/review status.

API keys/secrets are never stored in these tables.

## Offline synchronization

```text
content_revisions
  └── content_tombstones

profiles ── sync_checkpoints
```

Student PWA will sync using ordered server revisions and explicit deletions instead of relying on cache timestamps.

## Local-only data

Current product behavior for personal notes can remain local/account-scoped in Student IndexedDB unless a later business decision adds cloud note synchronization. Keeping local-only notes does not require a PostgreSQL notes table.

## JSONB policy

JSONB is allowed for bounded metadata/configuration/snapshots such as:

- asset source metadata;
- achievement rule config;
- AI input/output payloads;
- job error/validation detail.

Core relationships, ownership, ordering, codes, questions, options, attempts and entitlements stay relational.

## Delete policy

- Student-owned derived data: cascade with profile where privacy requires it.
- Curriculum referenced by historical attempts: restrict/archive instead of destructive delete.
- Lesson assets: cascade from lesson only when the lesson is truly removed through an intentional content operation.
- Access/redemption history: restrict important relationships; administrative deletion should normally become revoke/archive.
